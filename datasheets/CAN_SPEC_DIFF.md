# CAN 명세 ↔ 현재 코드 차이

**명세**: `내 공부/BMS_CAN_ID_명세.xlsx` (2026-06-25 작성 · 2026-07-10 갱신)
**코드**: `Core/Src/B_TEST_BMS_can.c` (2026-08-10 기준)

> ⚠️ **결론부터: 명세와 코드가 거의 전부 어긋나 있다.** 명세를 보고 만든 DBC·수신 코드는
> 지금 코드와 **한 프레임도 맞지 않는다.** RUN 데이터는 주소 대역 자체가 다르다.

---

## 1. RUN 데이터 — 주소 대역이 통째로 바뀌었다 🔴

명세는 **BOT `0x5xx` / TOP `0x6xx`** 인데 코드는 **`0x04x`** 를 쓴다.

| 프레임 용도 | 명세 (BOT / TOP) | 현재 코드 (BOT / TOP) |
|---|---|---|
| 결함/상태/알람 | `0x500` / `0x600` | **`0x040` / `0x044`** |
| 스택/팩 전압 | `0x501` / `0x601` | **`0x041` / `0x045`** |
| 전류/셀극값/온도 | `0x502` / `0x602` | **`0x042` / `0x046`** |
| SOC | `0x503` / `0x603` | **`0x043` / `0x047`** |

원인: 커밋 `06c727d Renumber CAN IDs: assign run-data SOC into 0x040 block` (2026-07-24).
명세 갱신일(07-10) **이후**에 코드가 바뀌었고 명세는 따라가지 않았다.

**프레임 내용(바이트 배치)은 명세와 동일하다.** 바뀐 건 ID뿐이다 — 단 SOC 프레임만 예외(§4).

---

## 2. TEST 데이터 — 일부는 살아남고 대부분 이동했다

명세는 **BOT `0x1xx` / TOP `0x2xx`**. 코드는 일부만 그 주소를 유지하고 나머지는 `0x04x`~`0x07F`로 옮겼다.

### 2-1. 명세 주소 그대로 살아있는 것 (레거시)

| 용도 | ID (BOT / TOP) | 비고 |
|---|---|---|
| 스택/팩 전압 | `0x111` / `0x211` | RUN 프레임과 내용 중복 |
| 전류 상세 | `0x112` / `0x212` | |
| 결함/상태/알람 | `0x120` / `0x220` | RUN 프레임과 내용 중복 |
| FET | `0x123` / `0x223` | **내용 변경됨 — §3 참조** |
| SOC | `0x133` / `0x233` | RUN 프레임과 내용 중복 |

### 2-2. 주소가 이동한 것 🔴

| 용도 | 명세 (BOT / TOP) | 현재 코드 (BOT / TOP) |
|---|---|---|
| 셀전압 ×4 | `0x101`~`0x104` / `0x201`~`0x204` | **`0x048`~`0x04B` / `0x051`~`0x054`** |
| 온도 A | `0x113` / `0x213` | **`0x04C` / `0x055`** |
| 온도 B | `0x114` / `0x214` | **`0x04D` / `0x056`** |
| Safety Alert/Status | `0x121` / `0x221` | **`0x05A` / `0x06D`** |
| Permanent Fail | `0x122` / `0x222` | **`0x05B` / `0x06E`** |
| 쿨롱 누적 | `0x130` / `0x230` | **`0x04E` / `0x057`** |
| 쿨롱 시간/CC2 | `0x131` / `0x231` | **`0x04F` / `0x058`** |
| CC3/보조전압 | `0x132` / `0x232` | **`0x050` / `0x059`** (내용도 변경, §3) |
| CUV 스냅샷 ×4 | `0x140`~`0x143` / `0x240`~`0x243` | **`0x05D`~`0x060` / `0x070`~`0x073`** |
| COV 스냅샷 ×4 | `0x150`~`0x153` / `0x250`~`0x253` | **`0x061`~`0x064` / `0x074`~`0x077`** |
| CB_Status2 ×4 | `0x160`~`0x163` / `0x260`~`0x263` | **`0x065`~`0x068` / `0x078`~`0x07B`** |
| CB_Status3 ×4 | `0x170`~`0x173` / `0x270`~`0x273` | **`0x069`~`0x06C` / `0x07C`~`0x07F`** |

### 2-3. 삭제된 프레임

| 용도 | 명세 ID | 사유 |
|---|---|---|
| 셀극값 / 전압 raw | `0x110` / `0x210` | RUN 전압 프레임(`0x041`/`0x045`)과 중복이라 통째로 제거 |

## 3. 내용이 바뀐 프레임 🔴

### 3-1. FET 프레임 (`0x123` / `0x223`) — 필드 2개가 빠졌다

| 바이트 | 명세 | 현재 코드 |
|---|---|---|
| 0 | `FET_Status` | 동일 |
| 1~3 | `CHG`, `DSG`, `PDSG` | 동일 |
| **4~5** | **`CB_Status1`** | **0** (→ `0x05C`/`0x06F`로 분리) |
| **6~7** | **`AlarmBits`** | **0** (삭제 — `0x040`/`0x044`의 Alarm과 중복) |

### 3-2. CC3 프레임 (`0x132`/`0x232` → `0x050`/`0x059`) — DLC가 8→6

| 바이트 | 명세 | 현재 코드 |
|---|---|---|
| 0~3 | `CC3_Counts` | 동일 |
| 4~5 | `Battery_Voltage_Sum` | 동일 (**단위 cV=10 mV 로 명기됨**) |
| **6~7** | **`LD_Voltage_Raw`** | **삭제, DLC=6** |

LD 핀이 TOP/BOT 모두 미사용이라 제거. **개요 시트의 "데이터 8바이트 고정(DLC=8)" 규정을 어긴다.**

### 3-3. SOC 프레임 (`0x043`/`0x047`) — 예약 바이트에 팬 정보

| 바이트 | 명세 | 현재 코드 |
|---|---|---|
| 0~1 | `SOC_Permille` | 동일 |
| **2** | **0 예약** | **팬 duty [%]** |
| **3** | **0 예약** | **온도 유효 플래그** (0 = 유효 온도 미수신) |
| 4~7 | 0 예약 | 동일 |

## 4. 신설된 프레임 (명세에 없음)

| ID | 용도 |
|---|---|
| **`0x080`** | MCU 보호 감시자 진단 — TripReason, BOTHOFF/latch 플래그, 크로스체크 카운터, 보드별 통신 실패 카운터 |
| `0x05C` / `0x06F` | CB_Status1 (FET 프레임에서 분리) |

## 5. 개요 시트의 서술과 다른 것

| 항목 | 명세 | 실제 |
|---|---|---|
| **송신 주기** | *"약 100 ms 주기 (HAL_Delay(100))"* | `HAL_Delay(63)` + I2C 지연 → **약 300 ms 추정** (`EVM_TEST.md` §6에서 실측 필요) |
| **DLC** | *"데이터 8바이트 고정 (DLC=8)"* | `0x050`/`0x059`만 **DLC=6** |
| 비트레이트 | 500 kbit/s | ✅ 일치 (Prescaler 10, Seg1 12, Seg2 3, PLL1Q 80 MHz) |
| 엔디안 | 빅엔디안 | ✅ 일치 |
| 전류 단위 | 10 mA, 부호 있음 | ✅ 일치 |
| 온도 단위 | 0.1 °C, 부호 있음 | ✅ 일치 |
| 자동 재전송 | DISABLE | ✅ 일치 |

## 6. 명세가 옳았고 코드가 틀렸던 것 ✅ (이미 수정됨)

명세는 처음부터 이렇게 적고 있었다:

> `Stack_Voltage / Pack_Voltage | uint32, 단위 mV (**BQ raw x 10**)`
> `*_Raw 전압류 | Stack/Pack은 **10mV 단위** raw`

그런데 코드는 issue #27 리뷰 때 이 ×10을 **제거**했고(`0ee61c2`), 그 결과 16S 67 V가
부호있는 16비트에서 **32767에 포화**되어 있었다.

PR #32에서 `DAConfiguration`을 `0x06`(센티볼트)로 되돌리고 ×10을 복원했다.
**즉 이 항목은 명세가 처음부터 맞았고, 코드가 이제 명세를 따라잡은 것이다.**

## 7. 권고

**정본을 하나로 정해야 한다.** 지금 명세가 3벌이고 전부 내용이 다르다:

| 파일 | 상태 |
|---|---|
| `내 공부/BMS_CAN_ID_명세.xlsx` | 가장 상세(비트맵 포함). **ID는 옛것** |
| `datasheets/bms can.xlsx` | 또 다른 ID 체계(0x040~0x07D). **역시 옛것** |
| `datasheets/bms_can_id_spec.csv` | **코드와 유일하게 일치.** 단 비트맵 설명 없음 |

- [ ] **`bms_can_id_spec.csv`를 정본으로 확정**하고 나머지 xlsx 2개는 폐기 또는 `_구버전` 표시
- [ ] `BMS_CAN_ID_명세.xlsx`의 **비트맵(Fault_Bits) 시트는 살릴 것** — 코드/CSV에 없는 정보이고 품질이 좋다. CSV 옆에 별도 md로 옮기는 것을 권장
- [ ] 개요 시트의 **송신 주기(100 ms)** 를 실측값으로 갱신
- [ ] 개요 시트의 **DLC=8 고정** 서술을 "`0x050`/`0x059`는 6바이트" 로 정정
- [ ] RUN 대역을 `0x5xx`/`0x6xx`로 되돌릴지, `0x04x`를 유지할지 결정
      (차량 전체 CAN 맵에서 다른 노드와 충돌하지 않는지 확인 필요 — `0x04x`는 우선순위가 매우 높은 대역이다)

> 📌 마지막 항목이 실제로 중요하다. CAN은 **ID가 낮을수록 우선순위가 높다.**
> RUN 데이터를 `0x5xx`에서 `0x04x`로 옮긴 것은 BMS 프레임의 버스 우선순위를 크게 올린 것이고,
> 모터 컨트롤러·MPPT 등 다른 노드의 ID와 충돌하거나 그들을 밀어낼 수 있다.
> 차량 전체 CAN ID 할당표와 대조가 필요하다.
